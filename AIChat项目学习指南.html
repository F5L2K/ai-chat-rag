1.2 重点：生成器 yield —— 流式输出的地基

这是全项目最关键的语法点。打字机效果、流式回复，全靠它。先看普通函数和生成器的区别：

# 普通函数：一次性算完，把完整结果 return 给你
def normal():
    result = []
    for i in range(3):
        result.append(i)
    return result          # 你拿到的是一整个列表

# 生成器：用 yield 代替 return，一次吐一个，吐完暂停，下次继续
def generator():
    for i in range(3):
        yield i             # 吐一个就暂停，等别人来要下一个

yield 的本质：函数执行到 yield 时暂停并返回值，下次被调用时从暂停处继续。所以生成器像一条「流水线」——生产者和消费者可以同时工作，不用等全部生产完。

为什么要这样？ 大模型生成一段回答可能要 10 秒。如果等它全部生成完再一次性给你，你要干等 10 秒；用生成器，模型吐出一个字就立刻推给你一个字，你看到的是「边生成边打字」——这就是打字机效果。

项目里的第一处：后端逐字推送（backend.py）

# backend.py · /api/chat 接口内部 —— 节选
def generate():                        # 这是一个生成器函数
    full_reply = ""
    stream = client.chat.completions.create(
        model="deepseek-v4-pro",
        messages=full_messages,
        stream=True,                   # 关键：让 DeepSeek 也"流式"返回
    )
    for chunk in stream:               # 每来一小块
        delta = chunk.choices[0].delta
        if delta.content:
            full_reply += delta.content
            yield delta.content        # ① yield：把这几个字立刻推给前端
    save_message(req.session_id, "assistant", full_reply)  # 流结束了再落库

# ② StreamingResponse 把生成器包成 HTTP 流式响应
return StreamingResponse(generate(), media_type="text/event-stream")

项目里的第二处：前端逐字接收（frontend.py）

# frontend.py · stream_ai_reply —— 节选
def stream_ai_reply(session_id: str, message: str):
    res = requests.post(BACKEND_CHAT_URL, json={...}, stream=True)
    for chunk in res.iter_content(decode_unicode=True):  # 来一块收一块
        if chunk:
            yield chunk              # 前端也是个生成器，转发给 st.write_stream

# st.write_stream 吃一个生成器，自动实现打字机效果
ai_reply = st.write_stream(stream_ai_reply(session_id, user_input))
理解闭环：后端生成器 yield 逐字吐 → StreamingResponse 转成网络流 → 前端 iter_content 逐块收 → 前端生成器再 yield → st.write_stream 逐字显示。整条链都是「生产一个、消费一个」，没有任何一方需要等全部。

1.3 异常处理：错误要分类，不能一锅端

调用外部大模型，什么错误都可能发生（网络断了、密钥错了、请求太频繁）。后端把错误分成 5 类，每类给用户不同的提示：

# backend.py · generate() 内部 —— 节选
try:
    stream = client.chat.completions.create(...)
    ...
except APITimeoutError:      yield "\n\n[错误] 模型响应超时，请稍后重试"
except APIConnectionError:   yield "\n\n[错误] 连不上 DeepSeek 服务，请稍后重试"
except RateLimitError:       yield "\n\n[错误] 请求太频繁，请稍等几秒再试"
except AuthenticationError:  yield "\n\n[错误] 服务配置有误，请联系管理员"
except APIStatusError:       yield "\n\n[错误] DeepSeek 服务返回错误，请稍后重试"
except Exception:            yield "\n\n[错误] 生成过程中出现异常，请稍后重试"

两个细节：流开始前的错误用 HTTPException（能返回 4xx 状态码）；流开始后的错误只能往流里塞文字（状态码已经是 200，没法改了）。这就是为什么错误提示以 [错误] 开头——前端看到这个标记就不入库。

1.4 装饰器：@ 符号是干什么的

@app.post("/api/chat") 的意思是：把下面这个函数"注册"给 FastAPI，当有人 POST /api/chat 时，就调用这个函数。装饰器就是"给函数包装一层功能"的语法糖，你现在只需要知道：看到 @app.xxx = 这是后端的一个接口。

Web 后端 FastAPI

接口是怎么"接"出来的

2.1 先懂 HTTP：请求和响应长什么样

前后端通信走 HTTP，你只需要懂 3 件事：

  • 方法：GET 拿数据、POST 提交数据、DELETE 删数据。项目的 6 个接口都用到了。
  • 状态码：200 成功、400 参数错、404 找不到、500 服务器内部错。前端靠状态码判断成败。
  • JSON：前后端传数据的通用格式，形如 {"session_id": "abc", "message": "你好"}。

2.2 接口一览：这个项目就是 6 个 API

接口干什么触发时机

2.4 中间件：每个请求先"过一道"

中间件在请求进入接口之前和之后各执行一段代码。项目用它给每个请求分配短 ID 并记日志：

# backend.py · log_requests —— 节选
@app.middleware("http")
async def log_requests(request, call_next):
    request_id = uuid.uuid4().hex[:8]      # 给这个请求一个 8 位短 ID
    request.state.request_id = request_id  # 存起来，接口内部能取
    started = time.perf_counter()
    response = await call_next(request)    # 放行，执行真正的接口
    logger.info("[%s] %s %s -> %d 耗时=%.0fms", ...)  # 记日志
    response.headers["X-Request-ID"] = request_id
    return response

作用：出问题时，终端日志里的 [a1b2c3d4] 能帮你定位是哪一次请求。

2.5 重点：SSE 流式响应 —— 接口怎么"边生成边返回"

普通接口：算完 → 一次性返回。流式接口：算一点 → 推一点。FastAPI 的实现方式是 StreamingResponse：

# backend.py /api/chat 结尾
return StreamingResponse(generate(), media_type="text/event-stream")
# ① generate() 是生成器：yield 一次 = 推一块给前端
# ② text/event-stream 是 SSE（Server-Sent Events）标准格式
# ③ 前端 requests 拿到的是"流"，iter_content 逐块读
关键限制：流式接口一旦开始推送，状态码就不能再改了（永远是 200）。所以项目把错误分成两段处理：流开始前的错误返回 4xx；流开始后的错误在流里塞 [错误]... 文字。看懂这一点，就理解了 frontend.py 里 if "[错误]" not in ai_reply 这行代码为什么存在。

2.6 全局异常处理：最后一道兜底网

# backend.py —— 任何没被接住的异常都到这里
@app.exception_handler(Exception)
async def safety_net(request, exc):
    traceback.print_exc()   # 完整堆栈打后端终端（给开发者看）
    return JSONResponse(
        status_code=500,
        content={"detail": {"message": "服务器内部错误，请稍后重试"}},
    )   # 前端只收到一句干净的 JSON（给用户看）

大模型与 OpenAI SDK

AI 是怎么被"调"出来的

3.1 大模型 API 的本质：发文字过去，收文字回来

你的代码并不"内置"大模型，而是调用 DeepSeek 的在线 API。流程是：把对话历史打包发过去 → 大模型生成回复 → 收回来。OpenAI 的 SDK 只是帮你做 HTTP 请求的封装。

# backend.py —— 客户端初始化（整个项目只有这里需要密钥）
from openai import OpenAI
client = OpenAI(
    api_key=os.environ.get("dp_api_key"),   # 密钥从 .env 读，绝不写死在代码里
    base_url="https://api.deepseek.com",    # 指向 DeepSeek 的接口地址
)

3.2 messages 结构：AI 看到的是"一摞消息"

发给大模型的不是一句话，而是一整个消息列表。每个消息有 role（角色）和 content（内容）：

角色作用
system给 AI 定人设和规则（不显示给用户）。项目里 = 数学助手 + RAG 资料
user用户说的话
assistantAI 说过的话（上下文记忆靠它）
# backend.py /api/chat —— 组装发给 DeepSeek 的完整消息
system_with_rag = build_rag_prompt(req.message, request_id)   # 第4章重点
full_messages = [{"role": "system", "content": system_with_rag}] + history
# 形如：[{system: 人设+资料}, {user: 你好}, {assistant: 你好！}, {user: 1+1=?}]

注意：history 是从数据库读出来的历史，AI 的"记忆"就是这么实现的——每次把全部历史重新发一遍。

3.3 stream=True：让回复"一块一块"来

# 非流式（stream=False）：等全部生成完，一次性拿结果
resp = client.chat.completions.create(model=..., messages=..., stream=False)
reply = resp.choices[0].message.content

# 流式（stream=True）：返回迭代器，吐一块拿一块
stream = client.chat.completions.create(model=..., messages=..., stream=True)
for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.content:
        print(delta.content)   # 每块只有几个字
为什么叫"打字机效果"：大模型本质上是"预测下一个字"，流式就是把每个字生成出来就立刻给你。配合第 1 章的生成器，前后端整条链都流式，用户看到的就是逐字输出。

3.4 错误分类：5 类错误，5 句人话

见第 1.3 节。这里补充一个细节：AuthenticationError 分支里 故意不打堆栈，只记一句日志——因为堆栈里可能带请求头（含密钥）。这是安全意识，记住它。

练习
  • 把 deepseek-v4-pro 改成 deepseek-chat 或其他可用模型名，重启后端试试还能不能跑（了解模型名怎么配置）。
  • 如果去掉 system 消息只发历史，AI 会变成什么样？（提示：人设丢了，RAG 资料也没了）
  • 为什么每次提问都把全部历史发给模型？如果历史有 1 万条会怎样？（提示：成本、上下文长度限制）

RAG 知识库

项目的灵魂 · 检索增强生成

4.1 它解决什么问题

大模型的"知识"是训练时学到的，截止到某个时间点，而且不包含你的私有资料（员工手册、课程笔记……）。RAG 的思路一句话：提问时先从你的资料里检索出最相关的几段，连同问题一起交给 AI，让它"开卷"回答。

资料你的文档
→
切块+向量化存进向量库
→
提问时检索找出最像的 3 段
→
拼进提示词资料+问题
→
AI 回答基于资料作答

4.2 基础概念：embedding（词向量）

电脑不懂文字，但懂数字。embedding 模型能把一句话变成一个数字列表（向量），并且：语义相近的句子，向量也相近。比如「如何请假」和「请假流程是什么」的向量距离很近，和「今天天气」的向量很远。

# backend.py · LocalEmbeddings —— 用本地模型做向量化（免费、不依赖 API）
class LocalEmbeddings(Embeddings):
    def __init__(self, model_name):
        self._model = SentenceTransformer(model_name)   # bge-small-zh-v1.5

    def embed_documents(self, texts):   # 上传文档时：批量向量化
        return self._model.encode(texts, normalize_embeddings=True).tolist()

    def embed_query(self, text):        # 提问时：单句向量化
        return self._model.encode(text, normalize_embeddings=True).tolist()

「向量」先不纠结数学，你只需要记住：文本 → 向量 → 比距离，这个项目用的是 bge-small-zh-v1.5，约 100MB，第一次用到才下载（懒加载），下载走国内镜像 hf-mirror.com。

4.3 入库：上传文档后发生了什么

入口 POST /api/knowledge/upload → add_document(title, content)，4 步：

① 切块500字/块，重叠50
→
② 向量化本地模型
→
③ 入索引FAISS 存向量+原文
→
④ 落盘faiss_store/ + 元数据
# backend.py · add_document —— 节选
# ① 切块：长文档切成小块，块间重叠 50 字防意思被切断
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500, chunk_overlap=50,
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],  # 按段落→句子→标点逐级切
)
chunks = text_splitter.split_text(content)

# ②③ 转成 Document 对象（带标题元数据）→ 加入 FAISS 向量库
docs = [Document(page_content=chunk, metadata={"title": title}) for chunk in chunks]
get_vector_store().add_documents(docs)   # 内部自动向量化+建索引

# ④ 落盘 + 元数据入库
save_vector_store()                      # 存到 faiss_store/ 目录
conn.execute("INSERT INTO knowledge_docs (title, chunk_count) VALUES (?, ?)", ...)

为什么切块？ 一次发给模型的文字量有限；而且文档太长，检索"整篇"没有意义——切成小块后，检索能精确到"哪一段最相关"。

4.4 提问：检索增强怎么发生

入口 POST /api/chat → build_rag_prompt(message)，也是 4 步：

① 问题向量化只向量化最新这句
→
② 相似度检索FAISS 找 TOP 3
→
③ 拼 system prompt资料+防编造指令
→
④ 发 DeepSeek基于资料生成
# backend.py · retrieve_relevant —— 节选
def retrieve_relevant(query, request_id="-"):
    store = get_vector_store()
    if store.index.ntotal == 0:      # 向量库是空的：跳过检索，直接返回空
        return []
    docs = store.similarity_search(query, k=RAG_TOP_K)   # RAG_TOP_K = 3
    return [doc.page_content for doc in docs]            # 取回 TOP3 的原文
# backend.py · build_rag_prompt —— 把资料拼进提示词
context = "\n\n---\n\n".join(f"资料片段 {i+1}：\n{c}" for i, c in enumerate(chunks))
return (f"{SYSTEM_PROMPT}\n\n"
        f"以下是可能相关的参考资料，请根据资料回答用户问题。"
        f"如果资料里没有答案，就如实说不知道，不要编造。\n\n"
        f"===== 参考资料 =====\n{context}\n===== 参考资料结束 =====")

只向量化"最新一句问题"（不是整个历史）——因为检索要找的是"跟此刻问题相关的资料"，历史里的旧问题会干扰。这是代码注释里特意写明的设计决策。

4.5 三个值得记住的设计细节

设计为什么
向量库为空时跳过检索并打日志避免"静默降级"：模型拿不到资料却照常作答，出问题都不知道。记日志 = 排查的第一现场
懒加载（get_embeddings / get_vector_store）不传文档就不用加载 100MB 模型，后端启动快
旧索引损坏自动删除重建换了 embedding 模型后向量维度会变，旧索引必然加载失败，删掉重建最省事
prompt 要求"资料里没答案就如实说不知道"防幻觉：模型拿不到资料时会编造。明确指令是 RAG 降低编造的关键
练习
  • 上传一篇文档后，在知识库面板看到"切成 N 块"。想想 N 和文档字数、chunk_size=500 的关系。
  • 把 RAG_TOP_K 改成 1，问一个需要多段资料的问题，对比回答质量变化。
  • 不传任何文档直接提问，观察后端日志里的警告"向量库为空"，再对比上传文档后提问，体会 RAG 的差别。
  • 想一想：如果用户上传的是 PDF/Word，代码能处理吗？（提示：目前 upload 接口收的是 title + content 文本，文件解析还没做——这是一个可以扩展的方向）

Streamlit 前端

界面是怎么"画"出来的

5.1 最重要的心智模型：整页脚本每次交互都重跑

Streamlit 和传统网页不同：你每点一次按钮/发一条消息，整个 frontend.py 都会从头到尾重新执行一遍。如果每次都重新执行，状态不就丢了吗？于是有了 st.session_state——跨重跑保存数据的"内存抽屉"。

# frontend.py —— 会话 ID 的保存与恢复
if "session_id" not in st.session_state:        # 第一次跑（抽屉是空的）
    url_sid = st.query_params.get("session_id") # 优先从网址参数恢复
    st.session_state.session_id = url_sid or str(uuid.uuid4())
    st.query_params.session_id = st.session_state.session_id  # 写回网址，刷新不丢

这套组合拳的效果：刷新页面、切走再切回，当前会话都不丢——因为会话 ID 存在 session_state 里，还同步写进了 URL。

5.2 组件速览

组件用途
st.sidebar侧边栏容器（会话列表、知识库面板）
st.chat_message(role)聊天气泡，按角色区分用户/AI
st.write_stream(gen)吃生成器，自动打字机效果，返回完整文本
st.query_params读写网址参数（会话 ID 持久化）
st.rerun()主动重跑页面（新建会话后刷新界面）
st.chat_input底部聊天输入框

5.3 一次聊天的前端全流程

# frontend.py · 主区域 —— 节选
# ① 加载历史（首次或切换会话时）
if "messages" not in st.session_state or st.session_state.messages is None:
    res = requests.get(f"{BACKEND_HISTORY_URL}/{sid}", timeout=5)
    st.session_state.messages = res.json()["messages"]

# ② 渲染历史气泡
for msg in st.session_state.messages:
    with st.chat_message(msg["role"]):
        st.markdown(msg["content"])

# ③ 用户输入 → 立刻显示 → 流式回复 → 归档
user_input = st.chat_input("请输入你的问题")
if user_input:
    with st.chat_message("user"):
        st.markdown(user_input)
    st.session_state.messages.append({"role": "user", "content": user_input})

    with st.chat_message("assistant"):
        ai_reply = st.write_stream(stream_ai_reply(sid, user_input))  # 打字机

    if "[错误]" not in ai_reply:   # 流中出错的不归档（第2.5节讲过）
        st.session_state.messages.append({"role": "assistant", "content": ai_reply})

5.4 侧边栏：会话管理 + 知识库面板

侧边栏做了三件事：+ 新建会话（生成新 UUID 并清空消息缓存）、会话列表（每条 = 标题按钮 + 删除按钮，从 GET /api/sessions 取）、知识库面板（标题/内容输入框 → POST /api/knowledge/upload）。

切换会话的小技巧：switch_session() 把 st.session_state.messages = None（标记"需要重新加载"），下次重跑时 5.3 的①就会自动从后端拉新会话的历史——用 None 当"脏标记"。
练习
  • 在侧边栏加一个"清空所有会话"按钮（提示：需要后端加一个批量删除接口，或者循环调 DELETE）。
  • 把 st.write_stream 换回普通的 st.markdown（先攒完整回复再显示），体验打字机消失的差别。
  • 观察刷新页面后会话还在——用 st.query_params 解释为什么。

SQLite 数据库

状态是怎么"存"下来的

6.1 为什么用 SQLite

项目需要保存聊天记录，但不想装 MySQL 这种重型数据库。SQLite 就是"一个文件当数据库"——chat.db 就是个普通文件，跟着项目走，重启不丢，零配置。

6.2 表结构

# backend.py · 两张表 —— 节选
CREATE TABLE IF NOT EXISTS messages (          # 聊天记录
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT NOT NULL,                  # 属于哪个会话
    role        TEXT NOT NULL,                  # user / assistant
    content     TEXT NOT NULL,                  # 消息内容
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE IF NOT EXISTS knowledge_docs (    # 已上传文档的清单
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    title       TEXT NOT NULL, chunk_count INTEGER NOT NULL, created_at TIMESTAMP ...
);

6.3 操作模式 + 防注入

每个操作都是四步：连接 → 执行 SQL → commit → 关闭。注意参数一律用 ? 占位符：

# backend.py · save_message —— 节选
conn = sqlite3.connect(DB_PATH)
conn.execute(
    "INSERT INTO messages (session_id, role, content) VALUES (?, ?, ?)",
    (session_id, role, content),   # 值只当数据用，不会被当成 SQL 执行
)
conn.commit()   # 不 commit，进程退出数据就没了
conn.close()
为什么不能拼字符串？ 如果用 f"INSERT ... VALUES ('{content}')"，用户输入一句 '); DROP TABLE messages;-- 就能删掉整张表（SQL 注入）。? 占位符从根源上杜绝。

6.4 一个进阶技巧：窗口函数

侧边栏要显示"每个会话的第一句话当标题"。这需要：每个 session_id 取第一条 user 消息。用窗口函数 ROW_NUMBER() 实现：

# backend.py · list_sessions —— 节选
SELECT session_id, content, last_time FROM (
    SELECT session_id, content,
        ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY id) AS rn,  # 会话内排序编号
        MAX(created_at) OVER (PARTITION BY session_id) AS last_time
    FROM messages WHERE role = 'user'
)
WHERE rn = 1          # 只要每个会话的第 1 条
ORDER BY last_time DESC

现在看不懂没关系，先记住"窗口函数 = 在分组内做编号/统计"，用到了再查。

练习
  • 后端运行时，用命令行打开 chat.db：sqlite3 chat.db，执行 .schema 看表结构，SELECT * FROM messages; 看数据。
  • 给 messages 表加一个 source 字段（区分 RAG 回答/普通回答），会改哪些函数？
  • 把 content[:20] 的标题截断逻辑从 Python 挪到 SQL（提示：SUBSTR），对比两种写法的优劣。

工程与工具

让项目可运行、可协作、可排查

7.1 .env 与密钥管理

密钥不该写死在代码里，也不该进 git。方案是：.env 文件存密钥 → python-dotenv 读到环境变量 → 代码从环境变量取。而且 .env 在 .gitignore 里被排除。

# .env（本地文件，不入库）
dp_api_key=sk-你的密钥

# backend.py
load_dotenv()                          # 读 .env 进 os.environ
API_KEY = os.environ.get("DEEPSEEK_API_KEY") or os.environ.get("dp_api_key")
你已经踩过的坑：等号后多一个空格（dp_api_key= sk-...），读出来的密钥就带空格，鉴权失败。这类问题可以通过日志排查：启动时打印 API_KEY[:8] 看格式对不对。

7.2 依赖管理

requirements.txt 记录所有第三方库及版本要求。别人拿到项目执行 pip install -r requirements.txt 就能装齐。版本写法 fastapi>=0.110 表示"不低于此版本"。

7.3 Git 工作流（你已经实操过了）

改代码 → git add . → git commit -m "说明" → git push。三个要点：

  • 提交前看 git status，确认没有 .env 等敏感文件混进去
  • 提交信息写"这次改了什么"，别写"改了一下"
  • 被 .gitignore 忽略的文件不会出现在提交列表（PyCharm 里显示为特殊颜色）

7.4 日志与调试：出问题先看哪里

现象去哪查
前端提示"连不上后端"后端终端有没有启动？uvicorn 窗口是否还活着
